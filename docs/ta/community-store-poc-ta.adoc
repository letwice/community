== Description

=== Purpose of this document

This Technical Analysis defines the architecture, data model, API contracts, UI flows, security model, and delivery plan for a *lightweight, laptop-only proof of concept (PoC)* of the Community Store Project. It is written to a level of detail sufficient for an AI coding agent (or a human developer) to implement each service directly, without further architectural decisions required.

=== Source brief

The originating brief is the "🛒 Community Store Project Proposal" supplied by the stakeholder (summarised in <<business>>). This TA translates that brief into an implementable, scoped-down PoC.

=== External dependencies

==== Payment / banking
* No real bank or PSP integration in this PoC. EFT + escrow is *fully simulated* inside `service-product` (see <<payments>>). This is a deliberate scope decision, not an oversight — flagged again in <<risks>>.

==== Email / SMS
* No real mail or SMS provider is integrated. University-email and business-registration verification are *mocked* (see <<auth>>). `service-notification` writes rich-inbox notifications to its own table and logs would-be email/SMS payloads to the console/log file instead of dispatching them.

==== Identity verification
* No integration with a university student registry or a business registration (CIPC-equivalent) registry. Verification is a manual backoffice action performed by a simulated "Admin" actor.

[[business]]
== Business

=== Problem statement

University campuses and their surrounding communities lack a single, trusted platform for affordable, sustainable trading and community engagement. Existing alternatives (informal social media groups, generic marketplaces) are fragmented and have no trust or verification mechanisms tailored to a campus community.

=== Goals for the PoC

* Prove the core trust loop: verified accounts → listings/activities → escrow-style transaction → mutual confirmation → review.
* Prove the multi-role model (student, vendor, community leader, faculty) with materially different permissions and UI surfaces.
* Prove a Lithium-like microservice decomposition can be stood up quickly and cheaply on a single laptop, as a feasibility signal before any investment in a production build.
* Produce artifacts (this TA, ERDs, sequence diagrams, risk register, sprint plan, Postman collection) that support a legitimate sign-off decision.

=== Explicit non-goals for the PoC

* No real payments, no real money movement.
* No production-grade security hardening, HA, autoscaling, or multi-environment pipeline.
* No native iOS/Android app. See <<frontend-scope>> for what "mobile" means here.
* No real email/SMS delivery.
* No load/performance testing beyond basic smoke testing.

=== Personas / roles

[cols="1,3,3", options="header"]
|===
| Role | Can do | Cannot do
| Student | Browse products & community activities; buy products; review products they bought and activities they attended | Post products or activities for sale/publication
| Vendor | List/manage products; view sales dashboard (paid-out vs pending payouts); fulfil orders | Post community activities
| Community Leader | Post/manage community activities | Sell products
| Faculty | Everything a Vendor and a Community Leader can do (union of both role sets, per brief) | —
| Admin *(implicit infra role, not in original brief but required to action verification)* | Verify/reject vendor, faculty and community-leader accounts via backoffice | Buy/sell/post on behalf of others
|===

NOTE: A user may hold more than one role concurrently (e.g. a Faculty member is simultaneously Vendor + Community Leader by definition; a Student could separately apply to become a Vendor). The data model treats role as a many-valued attribute per user (see `user_role`).

[[frontend-scope]]
=== Frontend scope decision

The brief lists `service-ui (ui-network-admin)` using Java Swing/JavaFX as the only explicit frontend, but also describes a "mobile-first marketplace." For a laptop-only PoC these are reconciled as follows:

[cols="1,2,2", options="header"]
|===
| Surface | Who uses it | Technology (PoC)
| Mobile view | Student (primary), also usable read-only by any role | Mobile-first responsive web SPA (HTML/CSS/vanilla JS or a minimal framework), served statically, calling `service-product` / `service-user` / `service-notification` REST APIs directly. *Not* a native app — disproportionate effort for a laptop PoC; the mobile-first *experience* is proven via responsive web, not an app-store build.
| Desktop view | Vendor, Community Leader, Faculty, Admin | JavaFX desktop client (`service-ui-desktop`, styled after Lithium's `ui-network-admin`), running locally against the same REST APIs.
|===

This is a scope decision made on the stakeholder's behalf and must be re-confirmed at sign-off; it is recorded here so the AI/human implementer does not need to re-litigate it.

== Architecture

=== Service inventory

Mirrors `app-lithium-full` conventions (Maven multi-module per service, `/frontend`, `/backoffice`, `/system` API prefixing, Flyway migrations, `*Request`/`*Response` DTOs, no entity leakage) but scaled down for a PoC.

[cols="2,2,3,1", options="header"]
|===
| Service | Responsibility | Owns schema/tables | Port (local)
| `server-auth` | OAuth2 + JWT issuing/validation; registration hand-off; mocked verification-token issuance | `auth_credential`, `auth_verification_token` | 9600
| `service-user` | User profile, roles, status, verification workflow, banking details, payout summaries, session/activity tracking | `user`, `user_role`, `user_banking_detail`, `user_payout_summary`, `user_session_activity` | 9601
| `service-notification` | Notification creation & inbox (email/sms/rich-inbox simulated) | `notification` | 9602
| `service-product` | Product listings, community activities, orders/escrow, reviews | `product`, `product_image`, `community_activity`, `order_transaction`, `product_review`, `activity_review` | 9603
| `service-ui-desktop` | JavaFX desktop client for Vendor/Community Leader/Faculty/Admin | — (API consumer only) | n/a (desktop app)
| `web-mobile` | Mobile-first responsive web SPA for Student (and general browsing) | — (API consumer only) | 9700 (static server)
| `server-gateway` *(optional, see <<risks>>)* | Single entry point / reverse proxy, mirrors Lithium's `{{gateway}}` Postman pattern | — | 9500
|===

NOTE: Per the user's decision, all backend services share *one* MySQL schema/instance (`community_store`) for PoC simplicity — a deliberate, documented deviation from Lithium's "no shared databases between services" rule. Table ownership is still conceptually partitioned per service (see table above) so a later split into per-service schemas only requires a data migration, not a redesign.

== Data model

All tables live in a single MySQL schema `community_store`. Flyway migrations are per-service but numbered independently per service module (`V1__.sql`, `V2__.sql`, ...), applied against the same schema. Every table that references a user does so via the immutable `guid`, never the auto-increment `id`, per Lithium convention (supports future split into per-service schemas/databases without FK coupling).

== API contracts

Path prefixes mirror Lithium convention: `/frontend/*` (self-service), `/backoffice/*` (admin/ops), `/system/*` (internal service-to-service, not exposed through any public gateway). All endpoints require a bearer JWT except where marked *(public)*.

[[payments]]
== Escrow / EFT simulation

=== State machine

["plantuml"]
----
@startuml
[*] --> CREATED
CREATED --> AWAITING_PAYMENT : buyer checks out
AWAITING_PAYMENT --> ESCROW_HELD : buyer self-attests EFT payment\n(simulated escrow account display)
AWAITING_PAYMENT --> CANCELLED : buyer/vendor cancels before payment
ESCROW_HELD --> SHIPPED : vendor marks shipped
ESCROW_HELD --> DISPUTED : buyer raises dispute
SHIPPED --> DELIVERED_CONFIRMED : buyer confirms receipt
SHIPPED --> DISPUTED : buyer raises dispute
DELIVERED_CONFIRMED --> FUNDS_RELEASED : automatic, on confirmation
DISPUTED --> REFUNDED : admin resolution (manual, out of scope for automation)
DISPUTED --> FUNDS_RELEASED : admin resolution (manual, out of scope for automation)
FUNDS_RELEASED --> [*]
CANCELLED --> [*]
REFUNDED --> [*]
@enduml
----

=== Simulation rules

* On `POST /orders`, `service-product` generates a human-readable `escrowReferenceNumber` (e.g. `ESC-000123`) and returns it to the buyer — this stands in for "display escrow account number."
* There is no real bank integration: `confirm-payment` is a self-attestation endpoint (buyer declares they have paid). This is clearly labelled in the UI as *simulated* so it cannot be mistaken for a production payment flow.
* Vendor cannot call `mark-shipped` until `ESCROW_HELD`.
* `confirm-receipt` is the only trigger that moves money (conceptually) — it atomically sets `FUNDS_RELEASED`, stamps `funds_released_at`, and updates `user_payout_summary` for the vendor (`total_paid_out_amount += total_amount`, `total_pending_payout_amount -= total_amount`).
* A vendor cannot register/list products until `verification_status = VERIFIED` and must have an on-file `user_banking_detail` row (enforced at `POST /service-product/frontend/products`, checked via the `service-user` `/system/users/{guid}` call — extend that internal endpoint to also return `hasBankingDetails:boolean`).

[[auth]]
== Security

* *AuthN*: OAuth2 password/client_credentials grants against `server-auth`, JWT bearer tokens validated as Spring Security OAuth2 Resource Server on every downstream service.
* *AuthZ*: role claims embedded in the JWT (`STUDENT`, `VENDOR`, `COMMUNITY_LEADER`, `FACULTY`, `ADMIN`); enforced via `@PreAuthorize` at controller level, never in the controller body.
* *Mocked verification*: clearly labelled in UI and logs as simulated — no real university/business registry is consulted. This must not be presented to stakeholders as production-equivalent trust.
* *Banking details*: `account_number` stored encrypted at rest (e.g. AES-256 via Jasypt or a `@Convert` JPA attribute converter) even though this is a PoC — handling real-shaped PII data with the right pattern is itself part of what's being proven.
* *DTO boundary*: strictly enforced per house rule — no entity ever appears in a controller signature.
* *Input validation*: `@Valid` on all `*Request` DTOs; `LIKE` search on product title uses `starts-with` (`LIKE 'value%'`), never `%value%`.

== Non-functional requirements (PoC-scoped)

[cols="1,3", options="header"]
|===
| Attribute | PoC target
| Performance | Not benchmarked; smoke-tested for "feels responsive" on a single laptop with seed data (~50 products, ~20 users)
| Availability | None — single laptop, no HA, acceptable to restart containers
| Observability | `log.debug` for flow, `log.info` for state transitions (e.g. escrow status changes), `log.warn`/`log.error` per house convention; no external APM
| Data retention | Ephemeral — database can be reset between demo runs via `docker compose down -v`
| Accessibility | Best-effort responsive layout only; no WCAG audit for a PoC
|===

== Testing strategy

* *Unit tests*: each service, standard JUnit5 + Mockito, covering the escrow state machine transitions and RBAC guard conditions in particular (these are the two areas most likely to hide a logic bug).
* *Integration tests*: Spring Boot `@SpringBootTest` + Testcontainers MySQL per service, covering the full registration → verification → listing → order → review happy path.
* *Manual/API testing*: Postman collection (`docs/api/community-store-poc.postman_collection.json`, to be authored alongside implementation) exercising every endpoint in <<API contracts>>, using the gateway-variable pattern (`{{gateway}}` pointed at each service's local port in the absence of a real gateway).
* *No* automated UI testing of the JavaFX client or the mobile SPA in this PoC — manual click-through against the acceptance criteria below is sufficient.

== Acceptance criteria (PoC sign-off)

* [ ] A Student can register, browse products and activities, buy a product, and leave a review after `FUNDS_RELEASED`.
* [ ] A Vendor can register, be verified by an Admin, add banking details, list a product, fulfil an order end-to-end, and see their dashboard numbers update correctly.
* [ ] A Community Leader can register, be verified, and publish an activity that a Student can later review once its date has passed.
* [ ] A Faculty user can do everything a Vendor and a Community Leader can.
* [ ] All data lives in MySQL via Flyway-managed migrations; the whole stack starts via `docker compose up` plus two locally-run clients (JavaFX, mobile SPA).
* [ ] This TA, the ERDs, the sequence diagrams, and the risk register are reviewed and signed off by the stakeholder before any production-track TA is started.

=== Risk register

[cols="3,1,1,4", options="header"]
|===
| Risk | Likelihood | Impact | Mitigation
| Simulated escrow/payment is mistaken by stakeholders for a production-ready payment flow | Medium | High | Explicit "SIMULATED" labelling in UI and in this TA (<<payments>>); sign-off checklist calls this out by name
| Mocked identity verification gives false confidence in trust/safety story | Medium | High | Documented as a non-goal (<<business>>); a follow-on TA must specify a real registry/KYC integration before production
| Shared single-schema database becomes entangled and hard to split later | Low | Medium | Tables are already partitioned conceptually per owning service and keyed by `guid`, not FK to `id`, to ease a future split
| Solo/small-team timeline slips given breadth of 4 services + 2 clients | Medium | Medium | Desktop and mobile clients are thin REST consumers by design; if time is short, Postman/manual API testing can substitute for one client at demo time
| JavaFX skill/tooling availability | Low | Medium | Fallback: demo the desktop role flows via Postman + the mobile SPA if JavaFX setup stalls
| No automated UI tests | High | Low | Accepted for PoC scope; mitigated by backend unit/integration test coverage on the logic that actually matters (escrow state machine, RBAC)
| Single laptop = single point of failure for the whole PoC | High (by design) | Low | Acceptable for PoC; `docker compose down -v` / `up` gives a clean reset before any demo
| Scope creep toward production concerns (HA, real payments, real verification) during the PoC window | Medium | Medium | This TA's non-goals section is the standing reference; any such request requires a new TA, not an in-flight scope change
